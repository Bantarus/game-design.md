# v0.3 conformance correction (2026-09-30)

> Correction note for [v0.3](v0.3.md). The v0.3 texts are left as released; this note records what they overstated. Logged as [OI-005](../../DECISIONS.md) (result) and [OI-006](../../DECISIONS.md).

## What v0.3 claimed

The README, the v0.3 release notes and spec §9.8 state that **all 12 in-repo trees lint clean** (0 errors, 0 warnings). That statement is true and still holds.

The overstatement is what "lint clean" was taken to imply. Spec §11 lists `gdmd lint` exit 0 as conformance item 1, and §6.2 says the linter validates each content entity against its content-schema. Spec §10 calls `schema/game-design.schema.json` the normative frontmatter schema. Read together, the texts imply that a lint-clean tree is schema-valid and has schema-validated content. **The linter checks neither.** It imports no JSON Schema validator, and has no rule for §6.2 (a)–(c) (OI-005).

## What a direct check finds

A one-off, read-only pass over the 12 trees (4 examples, 2 benchmark games, 6 starters) on 2026-09-30, at commit `3e44035`. It used the package's own YAML loader and `jsonschema` Draft 2020-12.

**§11 item 4 / §6.2 (content entities vs their content-schema).**
- 16 content-schema files; 29 entities linked through a `data_dir`.
- All 29 pass (a) schema validation, (b) `id` == filename stem, and (c) `status` + `implemented_in` present.
- **One entity is linked to no schema.** `templates/starters/party-rpg/gdd/content/heroes.md` has no `data_dir` (and no `count_target`), so `content/heroes/example_hero.yaml` is covered by no content-schema. It would validate if linked. §11 item 4 is therefore not met for the party-rpg starter, which `gdmd init --genre party-rpg` copies into every new party-rpg tree.

**§10 (frontmatter vs the normative JSON Schema).** 158 frontmatter blocks checked; **10 fail, in 8 of the 12 trees**, in three classes:

| Class | Files | What fails |
| --- | --- | --- |
| A. Whole-namespace `applies_to` refs | 8: `architecture-invariants.md` in `benchmark/games/{platformer,survival}` and in the starters for deckbuilder, party-rpg, platformer, survival, tcg and tick-combat | `applies_to: ["{resources}"]` etc. `$defs.TokenRef` requires 2–6 segments. **The spec's own §4.11 example uses this form**, while its prose says "`{namespace.id}` refs". The spec contradicts its schema here, not only the trees. |
| B. `cost:` objects without `resource` / `amount` | 1: `benchmark/games/survival/gdd/mechanics.md` (all 9 player verbs; first counted as 8) | `cost: { time_cost: { in_game_minutes: … }, consumes: … }`. `$defs.Cost` admits only an integer, a string, or `{resource, amount}`. The survival starter places `time_cost` differently and passes. |
| C. Content-schema missing required keys | 1: `templates/starters/party-rpg/gdd/content/heroes.md` | `data_dir` and `count_target` are required by `$defs.ContentSchemaFile`. This is the defect behind the unlinked entity above. |

The four canonical examples (`deckbuilder`, `party-rpg`, `tcg`, `tick-combat`) are schema-valid, and all of their content entities validate.

## Corrected statement

At v0.3, all 12 in-repo trees lint clean. The four canonical examples also meet §11 items 1–5 and validate against the JSON Schema. The two benchmark games and all six starters fail the JSON Schema: class A in all eight, plus class B in the survival benchmark game and class C in the party-rpg starter. The party-rpg starter additionally fails §11 item 4. Lint-clean does not imply §11 conformance until OI-005 and OI-006 are resolved.

## What is not changed here

Nothing is fixed in this note. Each class needs a decision about whether the tree or the schema/spec is wrong; class A in particular may be a schema fix rather than a tree fix. Fixing any of them changes either lint behavior or tree content, so each gets its own D-entry and commit (OI-005, OI-006). No new lint rule lands before that.

## Status after the v0.4 tree fixes (2026-09-30)

Classes B and C are fixed in the trees: class B by D-030 (the survival benchmark's verbs) and class C by D-031 (the party-rpg starter's `heroes.md`). The two-step pass below was re-run at `326cd50`:

- **§10:** 158 frontmatter blocks, **8 fail, all class A**: the `architecture-invariants.md` files of the two benchmark games and the six starters. Each fails only on whole-namespace `applies_to` items.
- **§11 item 4 / §6.2:** 16 content-schemas link 30 entities, and all 30 pass. No content entity is unlinked. The party-rpg starter now meets item 4.
- **Guard:** `tests/test_starter_schema.py` fails if a starter's frontmatter stops validating. The six class-A starter files are marked as expected failures until the class A decision.

**What remains:** class A only. Whether the spec's §4.11 example or the schema's `TokenRef` is wrong, and whether lint should run the schema at all, are decided after dogfood study 2 (OI-006). Until then, the corrected statement above still holds for class A: lint-clean does not imply §10 schema validity for the two benchmark games and the six starters.

## Class A resolved in the schema (D-033, 2026-09-30)

Class A was decided in the schema's favour. From v0.4, an invariant's `applies_to` item may be a whole-namespace reference such as `"{resources}"`: spec §3 defines it, `$defs.NamespaceRef` admits it, and lint and the views implement it.

- **The pass:** re-run after the fix, **0 of 158** frontmatter blocks fail across the 12 trees.
- **The guard:** the starter test's expected failures are retired, and every starter must now validate.
- **Trees scaffolded from a v0.3 starter:** their `architecture-invariants.md` validates against the v0.4 schema unchanged. It still fails the v0.3 schema, which predates the decision.
- **One behavior change to expect:** a `numeric_domain` invariant with `enforcement: lint` over `{resources}` (or `{entities}`) now checks every resource's bounds (or every collection's integer fields). Before, it checked nothing. A tree with a non-integer bound under such an invariant will see a new `invariant-violation`.

## Lint runs the schema (D-034, 2026-09-30)

From v0.4, `gdmd lint` validates every game-design.md file against the §10 JSON Schema (rule `schema-violation`, error), so lint-clean now implies §10 validity. §11 item 4 (content entities against their content-schema) is still not checked by lint (OI-005). A tree that was lint-clean at v0.3 but schema-invalid will see `schema-violation` errors at the offending fields: classes B and C above are exactly such cases.

## Trees scaffolded from the v0.3 party-rpg starter

Trees created with `gdmd init --genre party-rpg` at v0.3 carry the class C defect: `gdd/content/heroes.md` has no `data_dir` or `count_target`, so their heroes are covered by no content-schema. The starter is fixed in v0.4 (D-031). The fix for an existing tree is two frontmatter keys in `gdd/content/heroes.md`:

```yaml
data_dir: ../../content/heroes
count_target: 8   # use your tree's own entities.heroes.count_target from gdd/mechanics.md
```

## Reproduction

The check has two steps, both read-only. The first validates each tree file's frontmatter (`*.md` under the tree, and `*.yaml` excluding the `impl/` tree) with `jsonschema.Draft202012Validator(schema/game-design.schema.json)`, parsed by `game_design_md.loader.read`. The second validates each `*.yaml` under a content-schema's resolved `data_dir` against that file's `schema:`, then checks `id == stem` and the presence of `status` and `implemented_in`. Neither step writes to the repository.
